# User Manual — Project Planner

> **Status:** Official Documentation Verified
> Version 1.0
> **Last verified:** November 15, 2026
> **Documentation branch:** `Manual-update`
> **Audience:** Technical Team, Sub-Administrators, Administrators, and Super-Administrators
> **Accessibility Reference:** WCAG 2.2, Target Level AA

## 1. Purpose

This manual explains how to use Project Planner from the interface. It focuses on specific actions: where to enter, which option to choose, which button to press, and what result to expect.

It does not contain passwords, real emails, or integration secrets. Any screenshots included must use demo information.

## 2. System roles

| Role | Primary use | Common actions |
|---|---|---|
| **Technical Team** | Consult information and perform assigned work | View projects, schedules, orders, equipment, documents, and personal information. |
| **Sub-administrator** | Support operational management | Create and update projects, orders, technicians, and incidents when the option is enabled. |
| **Administrator** | Manage the system | Manage planning, portfolio, personnel, integrations, auditing, and roles. |
| **Super Administrator** | Governance and Recovery | Oversee administrators, backups, restores, and critical operations. |

> Some administrative capabilities depend on the effective configuration of server permissions. If a button does not appear, the account does not have access to that action, or you must log in again after a role change.

## 4. Reading conventions

- Names in quotation marks, such as **“Create Project”**, correspond to the visible text of a button or an option.
- The paths are shown like this: **Side menu → Portfolio → Create Project**.
- **Expected Result** describes the confirmation that should be seen upon completion.
- **If it doesn't work**, show the basic checks before requesting support.
- **Admin only** identifies actions that a technical account should not perform.

## 5. Expected catches

Each chapter includes a list of recommended screenshots. The images will be incorporated after validating this first version of the text and must:

1. show only fictitious data;
2. highlight the corresponding button with a number or box;
3. hide emails, passwords, tokens, and 2FA codes;
4. keep the same size and visual theme;
5. Indicate the role with which the capture was obtained.

## 6. Note on persistence

When an action is described as **persisted**, the change should be retained after reloading the page because it was saved by the backend. If a function is under validation or depends on the local state of the interface, the chapter will expressly warn of this.
